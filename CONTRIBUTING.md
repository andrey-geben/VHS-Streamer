# Как участвовать в разработке VHS-Streamer

Спасибо за интерес к проекту. Ниже — правила, которые помогают разбирать issues и pull request быстро и без лишних итераций.

## Сначала о лицензии

VHS-Streamer распространяется по **проприетарной лицензии** (см. [LICENSE](LICENSE)). Это не open-source-проект.

- Не отправляйте код, который вы не имеете права передавать проекту.
- Не копируйте фрагменты из проектов с несовместимой лицензией.
- Перед существенным pull request свяжитесь с автором: **andrey-geben@yandex.ru**.
- Отправка PR сама по себе не означает, что вклад будет принят. Для принятия может потребоваться письменное подтверждение прав и условий использования вклада.

Если вы не уверены, можно ли использовать чужой код, лучше сначала спросить.

## Что можно сообщить

- **Баг** — через issue-форму «Bug report».
- **Идею или улучшение** — через issue-форму «Feature request».
- **Уязвимость** — только по инструкции в [SECURITY.md](SECURITY.md). Не открывайте публичный issue.
- **Вопрос по эксплуатации** — сначала проверьте README, INSTALL_JETSON.md и существующие issues.

## Перед началом работы

1. Проверьте, нет ли уже открытого issue или PR по теме.
2. Для крупных изменений сначала обсудите подход в issue.
3. Не присылайте PR, который меняет поведение без описания и тестов.

## Локальная разработка

```bash
git clone https://github.com/andrey-geben/VHS-Streamer.git
cd VHS-Streamer
python -m venv .venv
```

Windows:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Linux:

```bash
source .venv/bin/activate
python -m pip install -r requirements-linux.txt
```

Для проверок, которые запускает CI:

```bash
python -m pip install PyYAML pytest ruff
ruff check .
python -m compileall -q *.py
pytest -q
```

## Стиль кода

- Следуйте настройкам `ruff.toml`.
- Не добавляйте зависимости без необходимости; объясните их в PR.
- Сохраняйте совместимость с версиями Python, которые поддерживает проект и CI.
- Не меняйте форматирование несвязанных файлов — это усложняет review.
- Публичные функции и модули сопровождайте понятными docstring/комментариями, если логика неочевидна.
- Не коммитьте `config.yaml`, логи, базы, сертификаты, ключи и другие локальные артефакты. Используйте `config.example.yaml`.

## Ветки и коммиты

- Делайте отдельную ветку под задачу: `fix/...`, `feat/...`, `docs/...`.
- Коммиты должны быть атомарными и понятными.
- В сообщении коммита указывайте суть изменения; для UI/поведения — что изменилось для пользователя.
- Не смешивайте рефакторинг и функциональное изменение в одном PR без необходимости.

## Pull request

В PR заполните шаблон и укажите:

- что и зачем изменено;
- как проверено;
- влияние на безопасность, совместимость и существующие конфигурации;
- скриншоты для изменений интерфейса;
- связанные issues.

Перед отправкой:

- [ ] `pytest -q` проходит;
- [ ] `ruff check .` проходит;
- [ ] `python -m compileall -q *.py` проходит;
- [ ] нет секретов, паролей, токенов и персональных данных;
- [ ] документация обновлена, если изменилось поведение;
- [ ] проверена обратная совместимость или описаны breaking changes;
- [ ] подтверждено право на передачу кода проекту.

## Ревью

Мейнтейнер может попросить изменения, тесты или объяснение. Это нормальная часть процесса. PR может быть закрыт, если:

- неясна цель;
- нет тестов на новое поведение;
- есть проблемы безопасности;
- вклад нарушает лицензию или права третьих лиц.

## Безопасность

Не публикуйте в issues:

- реальные IP-адреса и RTSP-URL с паролями;
- логи с токенами и учётными данными;
- дампы конфигурации;
- персональные данные.

Перед публикацией замените значения на `example`, `***` или `redacted`.
